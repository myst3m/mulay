# 105 — DW の配列は遅延した並び (VSeq) でも持ち、使う所が明示して扱う

状態: **採用 (作業中)** (2026-10-25。第 1 段: 値の型、書き手、選択子、組み込み関数の呼び出し。第 3 段 (2026-10-26): 純粋さの解析、並びのままの map・filter・flatMap・集計、payload の JSON を並びで読む)

## 決定

- DW の値に `VSeq q: Seq` を足す。`Seq` は「頭から読む読み手を作る関数」(`open`) を持つ。読み手は 1 回呼ぶごとに
  次の要素・終わり・`DwErr` を返す。何度でも頭から読める。型は Array (`val-tag` 5、`type-name` "Array")。
- **黙ってまとめて読まない。** `v/unmeta` などで勝手に配列にしない。並びを受け取る所が、流れのまま扱うか、明示してまとめて読むか
  (`v/seq-vec`、入れ子まで `v/whole-deep`) を決める。読む途中の誤りは DwErr として運ぶ (握りつぶさない)。
  - 組み込み関数: overload ごとに並びを受けるか (`rt/overload-seq`) を持つ。受けない overload を呼ぶ前に `rt/invoke` が上の段の
    並びをまとめて読む (`whole-args`)。
  - 書き手: JSON と NDJSON は要素を引き出しながら書く。それ以外の形式は登録表の入口で入れ子まで読んでから書く (`whole-then`)。
    書き手の誤りは DwErr (形式の誤りは種類 WriterException、並びを読む途中の DW の誤りはその種類のまま)。DW の境目 (rt/engine の
    `written-ns`、dw/engine) は、WriterException なら書き出しの誤り、それ以外なら評価の誤りとして示す。
  - 書き手は塊を流し出せる (`dw/fmt/out` の Sink、64 KB ごと)。今は呼ぶ側がまだ全体を 1 つの文字列で受ける (`fo/whole`)。
  - 選択子 (dw/sel): 値を再帰でたどる関数は `arr-items` で VArr と VSeq を同じに扱い、誤りを返す。非負の添字は先頭からたどって止まる。
  - update の添字と、オブジェクトへの展開は、並びをまとめて読んでから扱う。
- **DW の外へ出さない。** application/java の出力 (`java-out`) と、書き出した TypedValue に値を持つ所は、入れ子まで読んでから渡す。
  conn・rt・app の VArr を読む所は並びを見ない。
- **確かめ方**: 環境変数 `MULAY_DW_LAZY_ALL=1` で、DW の入力 (rt/engine の inputs の payload と変数、dwt の入力、DW の `read()`) の
  配列をすべて (入れ子も) VSeq にする (`v/lazy-input`)。本番で並びが生まれる所と同じ範囲。DW の golden とアプリのシナリオが、この設定でも通ること。
- `DwErr` は値より下の `mulay.dw.err` に置く (並びの読み手が返すため)。

## 理由

- 10 GB 級の入力を扱うには、DW の配列を全部メモリに持たずに流す必要がある。実 Mule は streaming の指定がなくても大きな入力を
  処理する (2026-10-25 に 1 GB で確かめた)。
- 形を決め打ちにした流し方 (ADR 054 の `payload map F`) は、書き方が少し違うだけで流れなくなる。値の種類として持てば、
  流れのまま扱える演算を増やすだけで広がる。
- 黙ってまとめて読む作りは、どこで流れが切れたかが見えず、読む途中の誤りも消える。使う所が明示して扱えば、誤りは正しく運ばれ、
  まとめて読んだ場所も記録できる (診断に使う予定)。
- 1 要素ずつの閉包の呼び出しは、まとまり (1024 要素) で引き出すより速かった (1,200 万要素の 2 段で 230 ms 対 500 ms)。

## 第 3 段 (2026-10-26)

- **純粋さ** (`mulay.dw.purity`): 並びのまま map などを返すと、関数は後で (読まれたときに、読まれた回数だけ) 呼ばれる。
  副作用のある関数 (uuid、now、random、log、readUrl、Timer、Runtime の run・eval・wait など、`rt/impure-builtin?`) を呼ぶ関数を後回しにすると、
  呼ぶ回数と順序が変わる。そこでコンパイル時に、スクリプトの関数ごとに「純粋か」を求める (`of-fns`、呼び出しを不動点までたどる。
  既定値の式も見る)。組み込み関数の Function の位置に中身の分からない関数 (変数など) を渡す関数は純粋としない。結果は `CProg` の `pure` に持ち、
  組み込み関数は `rt/env-pure?` で引く。純粋でない関数を受けたときは、並びをまとめて読んでから今までどおりに呼ぶ。
- **並びのままの組み込み関数** (dw/lib/core_coll、core): `map`、`filter`、`flatMap` は並びを返す。`reduce`、`joinBy`、`isEmpty`、`sizeOf` は
  要素を引き出しながら計算する。`flatMap` の関数が返した並びは、要素 1 つ分なのでその場でまとめて読む (閉包を Atom に持たない。Clay が循環を警告する)。
- **payload の JSON を並びで読む** (`rt/event/pipe-seq`): payload が読み直せる流れ (PIPE、512 KB を超える file:read など) で、形式が JSON
  (`format-id`、text/json も含む)、文字コードが UTF-8、読み手のプロパティが無く、中身が配列のとき、rt/engine の inputs は payload を並びにする。
  並びを開くたびに流れを fork し、終わりか誤りで捨てる。途中で止めた読み手の fork は、元の流れの owner (イベント) の終わり (`stream/leave`) で閉じる。
- **入力の誤り**: 並びを読む途中の JSON の誤りは専用の種類 (`dwe/input-err`、`mulay::InputReader`) にする。DW の `read()` の誤り
  (ReaderException) とは別。`try` と `orElseTry` は入力の誤りを捕まえずに通す (実 Mule では入力の読み取りはスクリプトより前に起きる)。
  rt/engine は入力の誤りを、使った場所の Trace を付けずに示す。実 Mule は JSON を評価の前に読み切る (索引を作る) ので、JSON の読み取りの誤りには
  Trace が付かない (全部読む道でも同じ。XML は評価の途中で読むので付く。fixture core-transform)。
- **誤りを捕まえる所**: `try` (と `orElseTry`) は、結果に並びがあれば入れ子まで読んでから成否を決める (実 DW の try は中身を評価し切る)。
  `default` と `?` は読まない。実 DW の map は遅延しているので、`(payload map ($ as Number)) default "d"` は誤りになり、
  `(payload map (if ($ == 2) fail("x") else {a: $}))[0].a?` は true になる (2026-10-26 に実 DW で確かめた)。

## 第 4 段 (2026-10-26)

- **payload の CSV を並びで読む** (`rt/event/csv-seq`、`dw/fmt/csv` の `stream-open`・`stream-next`): JSON と同じ条件 (読み直せる流れ、
  形式が CSV、文字コードが UTF-8) で、読み手のプロパティ (separator・header・headerLineNumber・bodyStartLineNumber・ignoreEmptyLine など。
  mime の引数と TypedValue のプロパティ) が正しいとき、rt/engine の inputs は payload を並びにする。値の meta は全部を読む道と同じ
  (reader-meta、mime に charset があれば encoding)。
  塊を足しながら 1 行ずつ読み、行が塊の端で終わっているときは、次の塊を足して読み直す (1 文字先まで見えるまで確定しない。`\r\n` が
  塊の境目で割れても空行にならない)。見出しの行と本文の開始行、空行 (ignoreEmptyLine) の数え方は全部を読む道と同じ。
  試験 test/fmt/csv_stream_test は、いくつもの文書とプロパティと塊の大きさ (1〜100,000 バイト) と、変異させた入力 600 個で、
  並びで読んだ結果と全部を読んだ結果が同じことを確かめる。
- 100 万行の CSV (45 MB) を map して JSON に書く flow は、ピーク RSS が 1,359 MB から 36 MB になった (ADR 107 の出力の spool と合わせて)。
- CSV の 1 行の読み取り (`read-record`) は、普通の文字を 1 文字ずつ足していたのを、続いた範囲をまとめて切り出すようにした
  (読むだけで 0.70 秒が 0.48 秒)。

## 第 5 段 (2026-10-26): 遅延したオブジェクト

- DW の値に `VOSeq q: FSeq` を足す。`FSeq` は頭から項目 (Field) を読む読み手を作る関数を持つ (VSeq の Seq と同じ形。何度でも頭から読める)。
  型は Object (`type-name` "Object"、`val-tag` 6)。使い道は 2 つ: 配列をオブジェクトに展開する `{(xs)}` (xs が並びのとき) と、
  大きな XML の読み手 (同じ名前の子が何百万も続く要素)。この段では値の種類と、それを読む所だけを足し、本番ではまだ作らない。
- 読む所 (VSeq と同じく、黙って作り直さず、読む所が明示して扱う):
  - `has-seq?`・`whole-deep` (入れ子まで読む)、組み込み関数: 並びを受けない overload は今までどおり `whole-args` で入れ子まで読む。
    並びを受ける overload (map・filter など) には、引数の一番上の遅延したオブジェクトだけを普通のオブジェクトにして渡す (`rt/top-objs`。
    遅延したオブジェクトを受ける組み込み関数はまだ無い)。
  - 選択子: `.k` は頭から読んで最初に見つかった所で止める (`sel/key-scan`)。他 (`.*k`・`..k`・`[n]`・名前空間つき・`.&k` など) は全部読んでから扱う。
  - 評価器: `<~` の meta、`{(x)}` の展開、属性の展開、`[?( )]`、`?` (頭から読んで見つかったら止める)、update、パターン `{k: v ~ t}`。
  - JSON の書き手は項目を引き出しながら書く (`json/write-oseq`)。`duplicateKeyAsArray` のときだけ全部読む。
    オブジェクトの項目の間でも 64 KB ごとに Sink に流す (前は配列の要素の間だけ。100 万項目のオブジェクトで出力が溜まり続けた)。
  - 読む途中の誤り (入力の読み取りの誤りなど) は握りつぶさずに返す。`?` は `exists-of` と同じく入力の誤りだけを通す。
- **確かめ方**: `MULAY_DW_LAZY_ALL=1` で、入力の配列に加えてオブジェクトも (入れ子も) 遅延したオブジェクトにする (`v/all-lazy`)。
  この設定で DW の golden 3500 (AOT も)・全アプリのシナリオが通る (足す前は 354 件が落ちた: 選択子 167、評価器 28、JSON の書き手 159)。
- **作る所** (2026-10-26): オブジェクトの組み立て `{..}` で、展開 `(xs)` の値が並び (VSeq) なら、その並びを部品として残し、
  前後の項目はまとまりで持って、全体を遅延したオブジェクトにする (`eval/ev-obj`、`parts-fseq`)。並びの要素ごとに
  `spread-fields` で項目にするので、入れ子の配列・null・オブジェクトでない要素の誤りは全部を読む道と同じ。他の項目は組み立ての時に評価する。
  AOT (`dw/gencode`) は展開を自分で組み立てるので、まだ遅延したオブジェクトを作らない (結果は同じで、メモリが減らないだけ)。
- 実 DW も展開を遅延する: `{(([1,2,3] map (if ($ == 2) fail("x") else {a: $})))} default "d"` は "d" にならず誤りになる (2026-10-26 に実 DW で確かめた)。

## 第 6 段 (2026-10-26): XML の payload を遅延して読む

- **lib/xml を塊で読めるようにする** (`reader-chunked`、`feed`、`next-chunk`): 読み手 (XmlReader は値) に、行・桁の起点 (`bline`・`bcol`)、
  入力の終わりに来たか (`eof`)、全部を読む状態か (`all`)、持ち越しのバイト (`tail`)、読んだバイト数 (`fed`) を足した。
  - 読む前に、読み始める位置から 1 単位 (開始・終了タグは `>` まで、注釈は `-->`、CDATA は `]]>`、処理命令は `?>`、テキストは次の `<` まで、
    XML 宣言は `?>` まで) がバッファに揃っているかを確かめ (`unit-ready`)、揃っていなければ「もっと要る」を返す。揃ってから今までの
    `next-event` で読むので、読み手の誤りはどれも本物の誤りで、テキストや `]]>` の検査が塊の境目で割れることもない。
    先に読んでみて、だめならやり直す形は、やり直しのために元の読み手を残すと記録 (30 欄) が毎回写されて遅くなる (xml2json で 6.6 秒) のでやめた。
  - `feed` は読み終えた前の部分を捨てて行・桁の起点を進め (`base-after`)、塊の終わりで割れた `\r` と UTF-8 の文字の途中は次の塊まで持ち越す。
    UTF-8 の検査も塊ごとに行い、誤りの位置 (バイト) は先頭からの数で示す。
  - DOCTYPE がある文書は、実体の展開が別の文字列に移るので、最後まで読み込んでから読む (`all`)。UTF-8 でない文書 (BOM や宣言の文字コード) は塊で読まない (`chunkable?`)。
  - 試験 test/xml/xml_chunk_test: 124 の文書 (expat と突き合わせた文書、CRLF、BOM、DOCTYPE と実体、誤りのある文書、2 行目より後の誤り) を
    1〜1,000,000 バイトの塊で読み、出来事の列と誤りの文言 (行・桁も) が全部を読む場合と同じ。
- **DW の XML の読み手** (`dw/fmt/xml`): 1 つの要素を組み立てる `build-node` と、塊を足しながら読む `pull` に分け、全部を読む道 (`build`) も
  遅延の道 (`lazy-read`) も同じ関数を使う。遅延の値は、文書全体を今までどおり `{根: ..}` のオブジェクト (meta 付き) にし、根の中身だけを
  遅延したオブジェクトにする (JSON の遅延が一番外の配列だけなのと同じ)。根の子の要素は、引き出された時にその部分だけを組み立てる。
  根の直下のテキストと CDATA は今までの Run で扱い、根を閉じた後も文書の終わりまで読む (根が 2 つある誤りなどを見落とさない)。
  根に子の要素が無い文書、XML 宣言が読めない文書、根の属性が maxAttributeSize を超える文書は遅延にしない (全部を読む道が同じ誤りを出す)。
  試験 test/fmt/xml_lazy_test: 文書と読み手のプロパティと塊の大きさで、遅延で読み切った値 (と誤りの文言) が全部を読んだ値と同じ。
- **`.*k`** は遅延したオブジェクトに対して並びを返す (`sel/multi-scan`)。該当が 1 つも無いときは今までどおり null を返すので、最初の 1 件だけ先に確かめる。
- **遅延を扱う状態かの判定**は、入力の一番上が並びかではなく、入力のどこかに並びがあるか (`has-seq?`) にした (XML の文書はオブジェクトの中に遅延したオブジェクトを持つ)。
- **入力の誤りの文言**: 並びを読む途中の入力の誤りは、全部を読む道と同じ `payload-err-desc` で文言にする (JSON は Trace なし、XML と CSV は
  スクリプトで payload を最初に使った位置の Trace)。
- 結果 (2026-10-26、CPU 0-3、tools/mule-bench の xml2json、142 MB): ピーク RSS が 2,007 MB から 36〜38 MB、出力は前とバイト単位で同じ。
  時間は 4.4〜4.9 秒から 5.3〜5.4 秒に遅くなった (1 単位の確かめ、遅延の読み手の 1 件ごとの手間、子の要素ごとの組み立て)。
  その後、読み手の時間の多くを占めていた clay の record の手間が clay 0.102.0 で直り、mulay 側でも UTF-8 の検査と 1 単位の確かめを
  軽くして、3,513 ms (実 Mule は 3,774 ms。2026-10-27、tools/mule-bench の測り方) になった。
- **子の要素を触った時に組み立てる案は採らない** (2026-10-27)。実 Mule (DW 2.11) の indexed reader は、字句を位置・長さ・深さ・名前の
  ハッシュとして long の配列に積み、値の文字列は触った時に元のバイトから作る。mulay で同じように子の要素を遅延にしても、縮むのは
  組み立ての一部だけで、天井を測ると 4% だった (xml2json で使わない region・qty・date を組み立てずに読み飛ばした版が 3.50 秒から
  3.36 秒、出力は同じ)。遅延の仕組み (閉包、位置、触った時の読み直し) を足せば残りはさらに減る。xml2json の内訳 (clay 0.102.0、
  呼び出しの連なりで振り分け) は、XML の読み手 42%、子の要素の組み立て 22%、選択・map・数への変換 22%、JSON の書き出し 11%。
  Mule の作りが効くのは字句の段がオブジェクトを作らないからで、mulay で同じ得を取るには、読み手が出来事 (variant・QName・Str) を
  作らずに DW の値を直接組む形にする (JSON の読み手と同じ形) 必要がある。目安: JSON は 114 MB を読んで値まで組むのに 339 ms、
  XML は 142 MB の出来事を数えるだけで 924 ms (バイトあたり 2.3 倍)。

## 第 7 段 (2026-10-30): XML の読み手が DW の値を直接組む

- **lib/xml の芯を字句の段 (`next-token`) にした。** 字句の種類 (`T-START` など、Int) を返し、物を作らない。
  - テキスト・注釈・CDATA・処理命令は窓 (`src`) の中の位置で渡す (`ta`・`tb`。テキストの終わりは `pos`)。参照を含むテキストは
    展開した Str で渡す (`ta` が -1)。開始タグの名前と属性は読み手の欄で渡す (名前の表の番号、属性の値の Str、名前空間は宣言の表の番号)。
  - 位置と欄が有効なのは次の `next-token` か `feed` まで (`feed` は読み終えた前の部分を捨てて位置を詰め、実体の展開は `src` を差し替える)。
    字句の後も残す名前 (開いている要素の段) は名前の表の番号で持つ。
  - 名前の表 (生の名前から、接頭辞・局所名・qname として正しいか・属性の種類) は FNV のハッシュの開番地法。上限 (65,536) に来たら、
    次の開始タグを読む前に、開いている要素の名前だけで作り直して番号を付け直す。1 つのタグを読む間は作り直さない (タグの中の番号が変わらない)。
  - `next-event` と `next-chunk` は、字句から出来事を組む包みにした。誤りの検査と文言は芯の 1 か所だけにある
    (DOM、SOAP、アプリの読み込みも同じ芯を通る)。DW 用に速い道を別に作って、だめなら出来事の道に戻す形は、誤りの文言を 2 か所で
    揃え続けることになるので採らなかった。
  - 塊で読む時は、1 単位が揃ったかを先に確かめる (`unit-ready`。タグを 2 度走査していた) のをやめ、読んでみて窓の終わりに来たら
    `T-NEED` を返す。誤りを見つけた時、入力の終わりでなく、タグがまだ閉じていなければ `T-NEED` を返し、揃ってから誤りを出す
    (前と同じ「単位が揃ってから誤りを出す」形なので、文言と位置は前と同じ)。注釈・CDATA・処理命令・DOCTYPE・XML 宣言は、前と同じく
    先に終わりを確かめる。第 6 段で避けた「読んでみてだめならやり直す」形が今度は速いのは、やり直しのために読み手を写さないから
    (欄を書き換えるのは単位を読み切った後だけで、それまでは窓を読むだけ)。
- **DW の読み手** (`dw/fmt/xml`) は字句から直接組む。開始タグの Key は名前の表の Str をそのまま使い、テキストは 1 回の `subs` で VStr にする。
  空白だけのテキストは、Run が空で、次が開始タグか子を持つ要素の終了タグなら Str にしない (どちらの場合も Run の規則で捨てられる)。
  Run の規則 (CDATA、`__text`、nullValueOn) は変えていない。
- **確かめ方**: test/fmt/xml_snapshot_test (642 の文書を読み手のプロパティ 6 通り、全部を読む道と塊の大きさ 6 通りの遅延の道で読んだ結果。
  期待は書き換え前のコードで作った。形は docs/fixtures.md)。test/xml/xml_token_test (同じ文書を塊の大きさ 7 通りで、字句の読み出しと
  出来事が同じ)。空白を飛ばす 2 つの条件と、字句の読み出しの 2 つを、1 つずつ壊すと落ちることを確かめた。
- **測った値** (142 MB の注文の XML、CPU 0-3): 出来事を数えるのに 5.49 Gcyc かかっていたのが、字句を数えるだけなら 3.10 Gcyc。
  xml2json は 3,468 ms・16.3 Gcyc・47.6 Ginsn (clay 0.105.0、書き換え前) から 2,556 ms・12.5 Gcyc・38.8 Ginsn (実 Mule は 3,881 ms・
  18.1 Gcyc。出力はバイト単位で同じ)。

  約 800 命令で、走査だけの捨てのループ (約 235 命令) との差は、記録の欄の読み書き (`clay_rec_get_*`・`clay_rec_with_*` と参照数の
  出し入れ) と関数の境目の手間。

## 残ること

- 実 DW の map は入力に関わらず遅延する。mulay は入力が並びのときだけ遅延するので、上の default と ? の 2 例は、入力が並びでないと実 DW と合わない。
  map・filter・flatMap を常に並びにする (印 lazy の決め方を、入力ではなくスクリプトに並びを作る呼び出しがあるかに変える)。
- 書き手の出力を spool に流す DW の境目 (今は `written-ns` が入れ子まで読んでから書く)。UTF-8 だけを流し、それ以外は全体を書いて符号化する。
  spool は event の owner の終わりで消す。
- 入れ子まで見る演算 (等しさ、比較、contains、indexOf、distinctBy、orderBy、Tree・Values・diff など) は、並びを受けない overload として
  rt/invoke が入れ子まで読んでいる。流れのまま扱えるもの (キーの選択子など) を増やす。
- ADR 054 の決め打ちの流し方の削除。foreach と batch で並びを要素ごとに回す。10 GB での確認。
- AOT が遅延したオブジェクトを作らないこと。
